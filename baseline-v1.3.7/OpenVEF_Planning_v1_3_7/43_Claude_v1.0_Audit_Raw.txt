1. Overall verdict
Gate
Status
Technical document gate V1–V7
FAIL. V1 and V5 now pass. V2, V3, V4 and V7 are partial, and V6 fails: seven of the 90 mandatory fixtures contradict the normative rules, and eight more are ambiguous. All the defects are document-level fixes
Owner-acceptance gate A1–A11
NOT MET. A1–A11 are PROPOSED / NOT ACCEPTED in files 16, 23, 32 and the README. No signature or date is recorded. The strict-AST branch (v1.0 "D1") is labelled OWNER CHOICE REQUIRED
Implementation / F18 execution
NOT RUN / NOT PASSED. No parser, assembler or fixture execution is claimed anywhere, and I ran none
Rationale. v1.0 is a large step forward:
• AST rules. The strict AST policy is now fully stated to the model, byte-identically in both arms.
• Diagnostics. The diagnostic grammar, enumerations, JSON-Pointer rule, failure map and evaluation order are repeated in file 25, essentially verbatim.
• Assembly. Assembly reproduces exactly, and every hash I recomputed matches the sidecar.
• Fixtures. All 90 fixtures are materialized, with correct hashes and no duplicates.
The gate still cannot pass, for two kinds of reason:
• Contradictory fixtures. Seven of the mandatory fixtures would make a correct parser fail F18: two have no create_driver, three put simulated run outcomes in the checker.source field, and three use error classes that are not in the map (M03 is counted in two of those groups).
• Rules that still lack one deterministic answer:
    ◦ which stage owns a module-level class or decorated function;
    ◦ which IMPORT_FORM_REJECT reason wins when several apply;
    ◦ non-ASCII identifiers inside an ASCII-only grammar;
    ◦ what happens to slots when a design halts mid-run;
    ◦ the clause-ID "near-match" rule.
No LLM call of any kind is permitted.
Scope of my checks. I made no LLM or provider calls and accessed no PDFs. I ran no project parser, assembler or harness. I did run bounded static scripts of my own:
• hash and length recomputation;
• extraction and rendering per file 31;
• jsonschema validation of the fixture response objects, applying the declared pointer sort rule;
• ast.parse on fixture sources (local Python 3.13, not the pinned 3.11);
• index, hash and grammar consistency checks.
These are audit checks. They are not F18 execution.

B3 (V3)
P §3.4 map row "Forbidden decorator …" and row "Disallowed import … prohibited built-in"; fixtures P27, M03, M34
The map assigns error class ENTRY_POINT_REJECT (stage AST_SIGNATURE) and IMPORT_POLICY_REJECT (stage IMPORT_POLICY). P27 and M03 expect error class DECORATOR_REJECT; M34 expects PROHIBITED_BUILTIN
The error_class key is sent to the model and compared by F18, so the two sources disagree on bytes
Either set the fixture error_class to the map value, or add DECORATOR_REJECT and PROHIBITED_BUILTIN as error classes in the map (Protocol and file 25 together)
B4 (V2/V4)
File 30 §3 "Shared AST rules"; P §3.4 order (3) vs (4); MODULE_STATEMENT_REJECT.reason=NON_FUNCTION_DEFINITION; M02
The shared module-level allow-list (imports, docstring, undecorated function defs, literal assignments) excludes class definitions and decorated functions. Read literally, it rejects even class Driver at step (3), IMPORT_POLICY. The map and M02 put class and decorator violations at step (4), AST_SIGNATURE. A module-level class Helper in checker.py therefore has two defensible outcomes
Stage, diagnostic and repair text are not deterministic, and the literal rule contradicts B5
Re-scope step (3) to statements other than ClassDef and FunctionDef (all class and decorator checks happen at step (4)), and define NON_FUNCTION_DEFINITION as "any other compound definition". Or move CLASS_FORBIDDEN and DECORATOR_REJECT to step (3). Pick one and align M02, M03 and P27
B5 (V2/V3)
File 30 §2 bullet 3; P §3.4 IMPORT_FORM_REJECT enumeration; P29a, P29b, P30
(i) There is no priority order when several reasons apply: from . import x (RELATIVE vs FROM_IMPORT_FORBIDDEN), from math import * (STAR vs FROM…), from __future__ import division (FUTURE_FEATURE vs FROM…), import os.path (IMPORT_NOT_ALLOWED vs SUBMODULE), import os as o (NOT_ALLOWED vs ALIAS), from os import path (NOT_ALLOWED vs FROM…). Only from collections import abc is resolved explicitly. (ii) import math, json (several names in one Import) breaks "one exact root" but has no reason code
Different conforming parsers emit different diagnostics
Add a total precedence for each Import and ImportFrom node, for example: RELATIVE → STAR → FUTURE_FEATURE → IMPORT_NOT_ALLOWED (root) → FROM_IMPORT_FORBIDDEN → SUBMODULE → ALIAS. Add reason MULTIPLE_NAMES. Add fixtures for each pair
B6 (V3)
P §3.4 grammar ("values are ASCII"); OFFENDING_ROOT, SYMBOL, NAME
Python 3 identifiers may be non-ASCII (import módulo, random.ñ, def é() with a decorator). These values are copied "as written", which breaks the ASCII rule, and no fallback exists. Separately, SyntaxError.offset can be None, and COLUMN has no fallback
The output for a reachable input is undefined
Add: "a non-ASCII identifier is replaced by the fixed token NON_ASCII_IDENTIFIER" (or reject it at step (3) with its own reason), and "COLUMN = 1 when the offset is absent or less than 1". Record that LINE and COLUMN follow the pinned CPython, so P25's column=5 must be re-confirmed on 3.11
B7 (V4)
P §3.4 DESIGN_HALT rows; §7, §7a
The map halts the design on a masked RTL/null divergence under an artifact's own stimulus, on a simulator error, or on a trace-integrity fault during slot evaluation. Undefined: (a) the triggering slot's fate (re-run the same frozen artifact after the evaluator repair, without a new LLM call?); (b) whether already-scored slots of that design are re-validated; (c) whether an evaluator repair counts as a packet or manifest change that triggers the §13.4 refreeze and F16 cycle; (d) an artifact that reproduces a simulator crash after repair (loop)
Slot accounting under ITT, and the freeze ordering, become non-deterministic mid-study
Add §7b, "Mid-run design halt": the slot keeps its frozen artifact and is re-evaluated after the repair, with no new generation; all slots of that design are re-run on the repaired evaluator; an evaluator change after packet freeze follows the §13.4 refreeze rule; a reproduced crash after one evaluator repair is classified TERMINAL/… (name it)
B8 (V6)
File 36; fixture index; P §3.4
(i) The dispositions ACCEPT_WITH_WARNING, CONTROL_EXPECTATION, F18_REJECT, DESIGN_HALT_NO_SLOT_SCORED and TERMINAL_INVALID_NO_REPAIR and the stages FEEDBACK_SERIALIZER and F18 are not defined in any normative document. (ii) PACKET_FREEZE_REJECT|RESERVED_HEADING_LINE, ASSEMBLY_REJECT|UNRESOLVED_PLACEHOLDER and F18_REJECT|VISIBLE_CLAUSE_ID_SET_MISMATCH (M18–M20) violate the CODE|key=value grammar and are defined nowhere. (iii) P22 and M12 express the same rule with different dispositions. (iv) M15's expectation depends on path regexes the pack never defines (and its input holds doubled backslashes)
The expected strings are not derivable from the contract
Add to file 36 §1 a normative disposition vocabulary and a separate "F18 assembly/manifest error codes" table (declared outside the model-feedback grammar). Unify P22 and M12. Define the three path regexes in P §3.4, or delete the redaction stage (the grammar already forbids paths) and drop M15
B9 (V7)
File 31 §3 bullet 2; file 38
clause_id_regex is anchored (^…$), yet it is used to search payloads "with token boundaries" that are never defined. "A near-match or malformed clause-like token is a packet-freeze error" has no pattern
The equality check is executable; the near-match rule is not
Define the search form (?<![A-Za-z0-9_-])[A-Z]{2,6}-[0-9]{3}(?![A-Za-z0-9_-]) and the near-match pattern (for example [A-Za-z]{1,8}-?[0-9]{1,5} not fully matching), or delete the near-match sentence
