1. Verdict: PASS WITH CORRECTIONS
v0.7 resolves the v0.6 metric, hypothesis and control-logic blockers in substance, not just in wording:
• T_i/X_i, the H2 family, the slot-level unit, the panel partition, the F16 floor, the power inputs and the owner approvals are all correctly specified.

The remaining defects sit in the prompt and repair layer. The actual templates introduce two treatment confounds and one instrument gap that the rules did not anticipate:
• the model-visible block IDs reveal the permutation;
• the task instruction's enumeration order matches ORG-A only;
• the "response schema" is not a schema.
The repair path also has an undefined context policy and an unbounded feedback channel that can leak golden outputs. These block F16 and F18, and therefore any LLM call. They do not block the hand-built harness work.

2.2 F15 identities: correct, but incomplete
The stated identities J_exposure = V · ΣX/(n_valid·|M|) and J_detection = V · ΣDET/(n_valid·|M|) are correct. They are, however, algebraic tautologies (V = n_valid/|G|), so they test arithmetic code, not the classifier.
Add these ledger identities, which do catch classifier bugs:
1.  Per valid artifact: |T_i| + |U_i| + |INVALID_PAIR_i| = |M_d|.
2.  Per arm and design: Σ_valid |M_d| + |invalid slots| · |M_d| = |G_cd| · |M_d|. Equivalently, the count of INVALID_ARTIFACT_SLOT ledger rows equals (|G_cd| − n_valid) · |M_d|.
3.  Per valid artifact: X_i ≤ |T_i|, DET_i ≤ X_i, and |U_i^X| ≤ |U_i|.
4.  Normal subset: NP_i + PND_i + DET_i = C_i ≤ |T_i|, with the miss-composition identity asserted on C_i only (already required).
5.  Panel: PanelCompat + PanelError + PanelFalseAlarmPartition = V_cd per stream, design and arm (already in F17).
2.3 Remaining classification inconsistencies
• N6: ANOMALY_PIPELINE_OR_NONDETERMINISM is ambiguous. It sits in T_i as "complete, unexposed". But a pipeline or harness nondeterminism means the trace itself is untrustworthy, so the pair's exposure status is not actually known. The validity rule already runs the checker twice on null, so a checker that later fails an identical trace is checker nondeterminism. A harness fault is an integrity violation.
    ◦ Fix: pre-register an adjudication rule. A harness or trace-integrity cause reclassifies the pair to INVALID_PAIR under precedence rule 1 ("predeclared determinism/integrity rule"). A checker cause leaves it in T_i. Report both counts. Without this, the class changes E_i's denominator through a post hoc judgment.
• N5: J_exposure is not "driver exposure". An artifact is valid only if its checker passes the null trace twice, so a good driver paired with a broken checker contributes zero ITT exposure. That is correct for an ITT endpoint, but C §2 ("driver exposure at a checker-independent specification mask") and C §1 describe exposure as checker-independent without qualification. State that the conditional E_i is checker-independent, while ITT J_exposure depends on the checker through the validity gate.
• Panel analogues are missing. The panel has no rule for (a) a corpus pair that violates the paired-input rule (exclude it from Q_ds at corpus freeze and report the count), or (b) a compatible checker returning FAIL on a mutant trace identical to its null trace (panel nondeterminism). Report both separately. Neither should be counted as detection.

3.2 Equal design weighting as an estimand: acceptable, with three conditions
With equal weights, the H2 estimand is Δ = ½(Δ_FIFO + Δ_UART): the unweighted average of per-design arm effects. It is not a pooled effect over slots or over mutants.
This is a legitimate and arguably the right estimand for a design-level question. It also has a useful property: because each per-slot J is already normalized by |M_d|, a design with many more mutants does not dominate. Three consequences must be stated, not discovered later.
1.  The design set fixes the estimand. The optional FSM (P §4) changes Δ from a two-design to a three-design average. Freeze the confirmatory design set before F16 and state that an optional design that is later dropped is not reweighted in (N13).
2.  Precision follows the noisiest design. For an unweighted average, Var(Δ) = ¼(Var Δ_FIFO + Var Δ_UART). If UART validity is near the floor while FIFO is high, the UART term dominates the variance. Power simulation must use per-design validity, not a pooled V (edit E9).
3.  Interpretation. A significant Δ with opposite-sign per-design effects is possible. Pre-register that per-design estimates are always shown beside Δ, and that sign disagreement is reported as heterogeneity, never as "no effect in design X". The Protocol already reports per-design estimates descriptively, which is sufficient once this sentence is added.
Within-design permutation. It is valid for the combined statistic provided the slot → arm assignment was randomized within design. The randomization schedule is TO FREEZE. Require it to be a within-design balanced assignment, generated from a frozen seed and committed before the first call (edit E10).
4. Prompt templates, F18, mask and reference-model boundary
4.1 What I verified directly in files 19, 20 and 25
• Both templates are 2,207 bytes. Each has three assembler-metadata lines, then nine [Name | Bn_ID] blocks.
• The block inventory is identical. Each block body is byte-identical across arms, both raw and after whitespace-trimming normalization. Both template bodies total 1,992 bytes. There are no CR characters.
• Orders:
    ◦ ORG-A: B0 B1 B2 B3 B4 B5 B6 B7 B8.
    ◦ ORG-B: B0 B2 B5 B1 B6 B3 B7 B4 B8.
    ◦ B0 (instruction) and B8 (response schema) are fixed first and last in both. Only B1–B7 move. This satisfies the "whole-block order only" rule as literally stated.
• The system and repair bodies (file 25) are shared single copies, so byte identity across arms holds by construction.
• No prompt text contains mask rows, reference-model content or mutant information. The prompts mention that an "observation mask" and "reference model/API" exist and are unavailable (B0; system body; repair body).
4.2 Defects in the actual templates
N1: Ordinal block IDs are model-visible (treatment confound). Headings such as [Design specification | B1_DESIGN_SPECIFICATION] are inside the model-visible body. In ORG-B the model reads B0, B2, B5, B1…, a sequence visibly out of order. ORG-B therefore carries an extra, non-semantic "shuffled document" cue that ORG-A lacks. Any arm effect would mix presentation order with the visible-disorder signal.
Fix: model-visible headings carry the name only ([Design specification]). Block IDs live only in assembler metadata. Alternatively, use non-ordinal IDs (for example, short random tokens) that are identical across arms.
N2: The instruction's enumeration order matches ORG-A only. B0 says "Follow the specification, legal-input rules, driver API, trace schema and checker contract exactly". The repair body repeats "specification, driver API, trace schema, checker contract and response schema". Both lists follow ORG-A's sequence. ORG-A is therefore instruction-congruent and ORG-B is not. The contrast becomes "congruent order vs. one incongruent permutation", a different treatment from "order alone".
Fix: replace both lists with order-free wording, such as "Follow every section of the authoring packet exactly". Otherwise, rename the factor and disclose it.
Related description issue (not a blocker): ORG-B is a single permutation with no stated construction rule. It looks interface-first: ports and driver API before the specification, envelope last. State its construction principle and limit generalization to these two orders (edit E4).
N3: The response schema is not a schema. B8 says to "Return exactly the required driver source, checker source, dependency declaration and a short assumptions manifest". It specifies no delimiters, file names, language or version, entry-point signatures, dependency allow-list or manifest format.
• The production parser (F16) cannot be frozen against prose. Parse-failure validity would then measure the parser's leniency rather than the arm.
• This is the generation-contract/execution-contract mismatch that collapsed SecTB-RTL's funnel to 9 production-valid outputs.
Fix: a machine-checkable format, for example one JSON object with fixed keys or fixed file-fence delimiters, exact entry points matching B5 and B7, an allowed-imports list, and a manifest row format with clause-ID citations. Freeze the parser and its reject rules with it.
N4: Repair path.
(a) Context policy is unspecified. The repair body says to "continue to obey the exact same specification", which implies a multi-turn continuation. Nothing states whether the original system message, user prompt and prior response are resent. A standalone repair message has no authoring packet and no arm ordering; a continuation has both. Freeze one policy, identical across arms: a continuation with the full prior turns resent byte-identically is recommended.
(b) The feedback field is an unbounded information channel. PERMITTED_BLACK_BOX_NULL_NETLIST_FEEDBACK_AND_LOGS has no whitelist, size cap or truncation rule.
• One repair trigger is "checker rejection on the null trace". Any feedback that includes the null trace, or diagnostics echoing its output values, gives the model the golden outputs for its own stimulus. That is exactly the expected-output table that P §3.2 withholds.
• Driver runtime logs can echo DUT outputs in the same way.
Fix: a frozen feedback grammar per stage:
• stage ID;
• error class;
• compiler or parser messages truncated to a fixed byte count;
• for checker rejection, only "checker returned FAIL on a legal null-netlist trace" (no row index, no values, no trace);
• no stdout or stderr from the driver beyond exception type.
If the owner prefers to allow the null trace, that is a legitimate choice, but it must be declared as golden-trace feedback and disclosed as such.
(c) Disclosure. Even under the strict grammar, repair on null-trace rejection is oracle-guided repair. Report validity both before repair (initial call only) and after k repairs.
N9: Assembly is unspecified. The pack does not define:
• which lines are stripped as metadata (lines 1–3 plus the trailing blank line?);
• the separator between blocks;
• trailing-newline handling;
• the encoding (UTF-8 without BOM);
• the exact canonical-normalization algorithm that F18 hashes against;
• placeholder escaping, if a payload contains {{ or [;
• the provider message-role mapping (system body → system role, template → a single user message).
"Same bytes after normalization" is only checkable once the algorithm is written. Freeze it as a short spec before F18.
N10 (minor): Mentioning the mask. Telling the model an "observation mask" exists hints that some outputs are unscored. It is identical in both arms, so it is not a confound. I would still drop the word from the model-visible text (use "evaluator-only materials"), because it invites lenient checkers.
4.3 Mask and reference-model boundary
• The rule is sound. The mask, reference model/API and expected-output tables are evaluator-only. Every mask row must map to an author-visible clause, and checkers are barred from reference calls (P §3.2, §9; D4).
• The traceability CSV (file 24) is a header row only. This is honest TO FREEZE, not a defect.
• Columns to add (N11):
    ◦ mask_variant (primary / strict);
    ◦ spec_version_sha256;
    ◦ author_packet_block_id (B1/B3/…), so each clause's block is known;
    ◦ clause_appears_in_blocks, which flags a clause duplicated across blocks. Duplication would change the relative position of content between arms.
• The file uses CRLF line endings, while the templates use LF. Normalize before hashing.
• Payload partitioning is unspecified. The specification (B1) and the reset/legal-input rules (B3) can overlap. Add a rule that each clause appears in exactly one block, or that duplication is recorded and identical in both arms.
