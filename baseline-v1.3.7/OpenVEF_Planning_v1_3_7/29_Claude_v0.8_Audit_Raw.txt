A. Verdict: FAIL for the LLM-call gate (narrow and text-level); the rest of the pack is sound
This audit's job, per 32_v0.8_Status_and_Gates.md, is to decide whether N1, N2, N3, N4 and N9 are now fixed concretely enough to unlock F16. You set the rule: no pass unless every one of them is concretely testable in the files.
• N1 and N2 meet that bar.
• N3, N4 and N9 do not, yet. The v0.8 files are a large improvement, but each still has a few requirements that are contradictory across documents, are hidden from the model, or cannot be implemented deterministically from the text.
None of these needs a methodological redesign. All are fixable by editing the existing files. They are also not "honestly TO FREEZE" parameters: each is a missing or conflicting rule, not a missing value.

1.2 N1: block IDs and arm cues — RESOLVED
• Headings are names only ([Task instruction] … [Response schema]). The IDs live only in 33_Prompt_Assembly_Sidecar_v0.8.json, which is marked model_visible: false.
• File 31 requires rejecting model-visible text that contains arm labels, B0…B8 or metadata. That is a concrete, testable F18 check.
• Minor: say how the match is done. A plain substring match on B1 would also hard-fail an otherwise valid design payload that happens to contain, say, a signal or state name B1. Use a word-boundary regex \bB[0-8]\b and require payload authors to avoid such tokens (C9).
• The visible schema contains the project name (OpenVEF … Response Schema v1.0, $id https://openvef.org/…). This is identical in both arms, so it is not a confound. It does tell the model it is inside a named evaluation framework, and the $id points to a domain the project may not control. Consider a neutral urn: ID (nit).
1.3 N2: order-free instructions — RESOLVED
• B0 now says "Follow every section of the authoring packet exactly". The repair body says "Continue to obey every section of the authoring packet and the response schema". Neither lists blocks in any arm's order.
• The remaining ordered mentions are congruent with both arms:
    ◦ "driver … checker": B5 precedes B7 in both;
    ◦ "specification … trace's recorded inputs": B1 precedes B6 in both;
    ◦ "response schema below": B8 is last in both.
• Minor (C10): the system body says to "Treat the design specification and interface contract as authoritative". Specification-then-interface is ORG-A's sequence; ORG-B puts the port manifest and driver API before the specification. This is weak, but it is the same kind of cue N2 removed. Replace it with "Treat the authoring packet as authoritative".
1.4 N3: strict output and entry points — PARTLY RESOLVED
What now meets the bar:
• one JSON object, no fences or prose;
• additionalProperties:false throughout;
• constant schema_version, language, language_version, filenames and signature strings;
• dependencies with maxItems:0;
• a structured assumptions array;
• duplicate-key rejection;
• no permissive recovery;
• the schema is inserted byte-exactly in both arms.
I validated a minimal conforming response: no errors.
Residual defects:
• N3-a: the hidden rules are not shown to the model. The model-visible text contains no import allow-list. File 30's 11-module stdlib list excludes, for example, __future__, copy, abc, operator, heapq and bisect, which a Python 3.11 author would routinely use. The model also never sees the checker return object ({verdict, diagnostics[{code, message, cycle, clause_id}]}). Both appear only in file 30, which is not model-visible.
    ◦ Unless the B5/B7 payloads restate them, validity will measure compliance with rules the model never saw.
    ◦ This is testable only if F18 is required to check that B5 and B7 state the allow-list, the driver sentinel and the checker return shape byte-identically to file 30. No such requirement exists yet.
• N3-b: Protocol §10 contradicts file 30. §10 says the checker returns PASS or FAIL "plus optional structured diagnostics". File 30 says the object "must contain exactly verdict and diagnostics", and that an invalid diagnostic is a checker error. A checker returning {"verdict":"PASS"} is therefore valid under §10 and a checker error under file 30. That changes V_cd, X_i (CHECKER_ERROR_AFTER) and detection.
• N3-c: signature checking is undefined. The schema forces the model to echo signature strings. My spacing test (dict[str,str] without a space) fails the schema, which adds formatting noise to validity; that is symmetric across arms but should be disclosed. Separately, file 30 says to reject "wrong entry-point signatures" without saying how the source is checked. A source can echo the right constant and define step(self, i, o), or omit annotations. Freeze an AST and inspect rule covering:
    ◦ a module-level create_driver with one positional parameter;
    ◦ a class Driver with a step method taking two positional parameters after self;
    ◦ a module-level check_trace taking two;
    ◦ whether annotations are required or ignored.
• N3-d: the clause-ID rule is untestable and self-contradictory. B8 says each assumption "must cite an author-visible clause ID" and, for unspecified items, "record that fact in the assumptions array". An unspecified item has no clause to cite. Neither the schema (minLength:1; my test with NOT-A-CLAUSE passes) nor file 30 checks the ID against the packet's clause list. Choose one:
    ◦ (i) the parser validates clause_id ∈ the frozen clause list, plus a reserved value such as UNSPECIFIED for gaps; or
    ◦ (ii) the assumptions are descriptive and never affect validity.
  Then state that choice in B8.
1.5 N4: repair conversation and feedback — PARTLY RESOLVED
What now meets the bar:
• same-conversation continuation;
• the full message array resent byte-identically (system, arm prompt, all assistant replies, all earlier repair messages), with no editing or truncation;
• exactly one feedback JSON object with three fixed keys;
• fixed stage/error pairs;
• a 2,048-byte cap;
• exception class name only;
• a fixed null-rejection sentence;
• an explicit ban on rows, row indices, values, waveforms, stdout/stderr and mutant data;
• oracle-guided-repair disclosure, with initial-call and post-repair validity reported separately.
The golden-output leak from v0.7 is closed.
Residual defects:
• N4-a: the trigger → stage map is incomplete. The four stages cover parse/schema, compile, driver runtime exception and checker FAIL on null. Protocol §7 and §13.1 also make the following failures invalidate a slot, with no stage assigned. For each, the pack must say either which stage and diagnostic it uses, or that it is terminal with no repair. Without that, F16 cannot be run deterministically.
    ◦ checker crash or invalid return object on the null trace;
    ◦ the two null-trace checker runs disagreeing (nondeterminism);
    ◦ a static import-policy violation;
    ◦ a wall-clock watchdog timeout (no exception class exists for this);
    ◦ an RTL-vs-null control failure;
    ◦ a driver returning an incomplete, extra-key or illegal input vector.
• N4-b: three documents disagree on PARSE_SCHEMA content.
    ◦ File 21 says "parser/schema reject code; no output values".
    ◦ The Protocol (§3.4) says "the redacted parser/compiler diagnostic … cap of 2,048".
    ◦ File 25 caps "Compiler/parser text" at 2,048 bytes.
  Pick one. I recommend a fixed reject code plus the JSON-pointer path of the first schema error. Raw validator messages can quote large spans of the model's own output and vary by library version.
• N4-c: the order of operations is unspecified. Freeze:
    ◦ (i) precedence when several stages fail (first failing stage in pipeline order, driver before checker);
    ◦ (ii) the order redact → truncate → JSON-escape;
    ◦ (iii) whether the 2,048 bytes are counted before or after escaping, and truncation on a UTF-8 code-point boundary with or without a fixed marker;
    ◦ (iv) the redaction rule as an explicit list. "Absolute paths and any trace/output-value excerpts" is not mechanical.
1.6 N9: assembly and canonicalization — PARTLY RESOLVED
What now meets the bar:
• encoding;
• metadata stripping (it matches the files);
• block parsing;
• rendering (my renderer reproduced equal-length arms);
• byte-exact schema insertion;
• the placeholder hard-error rule;
• the role map (system / user / assistant / user);
• the 7-step canonicalization;
• the archive and hash list.
Residual defects:
• N9-a: file 25 is outside the spec. File 31 never says how the system and repair bodies are extracted from file 25.
    ◦ It does not say whether text runs strictly between the --- BEGIN/END MODEL-VISIBLE … --- lines.
    ◦ Both bodies begin and end with a blank line (I checked), and no rule says whether these are trimmed.
    ◦ Nor does it say whether the repair message keeps the [VALIDATION_FEEDBACK_JSON] line and the two-space JSON indentation.
  The system and repair hashes, which F18 compares, are therefore not reproducible from the text. Add a file-25 section to file 31 with the same precision as the template rules.
• N9-b: the escape rule defeats itself. "Prefix that line with a backslash during parsing and remove only that escape backslash at render time" means the model sees a payload line identical to a real heading. That makes the prompt structure ambiguous to the model, and it would trip any duplicate-heading check run on the assembled prompt. Make a heading-identical payload line a hard error at packet freeze instead.
• N9-c: the sidecar is incomplete. File 31 requires the schema SHA-256 and inserted byte length to be recorded in the sidecar. The sidecar has neither. The schema is already drafted, so record 15f875519027ff8b82d1a99fefe24ef6b3c4b6daf0cace351dc14b5a50202997 and 2,543 bytes now, and add the payload-hash fields.
