OpenVEF Step 3 Audit: LLM-Era Verification Literature
Nov 22, 2026 · @Conductors
1. Executive verdict
Overall: CONDITIONAL GO. The research question must be rewritten before Step 4.
The Step 3 review is careful and mostly accurate. Every headline number I could check against a primary or author-hosted source matched. It still understates the prior art in three ways and leaves the central interpretive problem unresolved.
1.  The highest-value preprint was not fully readable here. I could only access the TechRxiv preprint's abstract: the PDF mirror and the TechRxiv page both blocked automated reads. The abstract confirms the core predicate: outputs differ between correct and faulty RTL, all tests still pass, therefore checkers are missing. It also confirms an approximately 80 s detection cycle. Step 3's finer claims (checker-dependent observability, 12 cases, 2 designs, one model) remain unverified by this audit. One discrepancy needs checking: the abstract says "automated fault injection", while Step 3 reports manual mutation injection.
2.  Step 3 missed a close new benchmark: DVBench (arXiv 2611.25066, Nov 2026). Agent-generated UVM testbenches are scored on golden acceptance, mutant detection, coverage and independent reference-model correctness across 95 tasks and 13 agent–model configurations, and a synchronous FIFO is its worked example. The authors state that mutation testing measures whether stimulus and checker together distinguish defects. That is exactly the coupling problem OpenVEF faces.
3.  CovR already substitutes components. It replaces CorrectBench's driver track with its own stimulus while keeping the downstream checker, and it already uses MCY-Yosys mutants (10 per design). The MCY fault population and component substitution are both precedented.
4.  The primary metric does not measure checker quality. PND/(NP+PND) describes the composition of misses for a coupled driver–checker pair. A prompt difference in that ratio is a valid total effect of the prompt on composition. It cannot be read as a checker effect, and the analysis conditions on artifact validity, which the prompt itself can change. Section 7 sets out the fix.

5. Novelty claims OpenVEF must not make
OpenVEF must not say, or imply in a title, abstract, poster or faculty email, that it is the first or a novel:
1.  LLM-generated testbench, driver/checker (hybrid) testbench, or offline Python checker. (AutoBench and successors)
2.  Use of mutants to evaluate LLM-generated verification artifacts, or mutation-based testbench qualification in general. (AutoBench, PRO-V, DVBench, AssertLLM2, GateTruth, SecTB-RTL; Certitude lineage)
3.  Method for detecting missing checkers from outputs that diverge while tests pass. (TechRxiv preprint; Certitude non-detected class; Huang 2015)
4.  Decomposition of verification misses into stimulus versus checker causes, or activation/propagation/detection analysis. (Functional qualification; Huang 2015; Verify the Verifier)
5.  Study of prompt arms for LLM-generated hardware verification artifacts, or a randomised, pre-registered prompt experiment in this area. (SecTB-RTL, LLM4DV)
6.  Use of Yosys/MCY netlist mutants for evaluating LLM-generated tests. (CovR; From FIPS to FPGA)
7.  Separation or substitution of generated stimulus and checking components. (AutoBench architecture; CovR substitution)
8.  Use of FIFO/UART benchmarks for this purpose. (GateTruth, TechRxiv, DVBench, data-integrity paper)
9.  "Checker quality" or "stimulus quality" measurement from PND/(NP+PND) alone. This is a validity problem rather than a novelty one, but it would be the first thing a reviewer attacks.
Never write "no prior work" or "to our knowledge, the first". Write "not found in the sources we searched (list, dates)".
6. Defensible candidate contribution statement
OpenVEF is an open, reproducible measurement study of LLM-authored hardware verification artifacts. For cycle-exact sequential RTL designs and a declared population of post-synthesis netlist signal mutants, it records per artifact where verification fails: whether the artifact is valid, whether its stimulus exposes a fault at outputs defined by a pre-frozen, checker-independent specification mask, and whether its own offline checker then rejects the faulty behaviour. It estimates how two prompt structures carrying identical design information shift each stage. Mutation-based testbench evaluation, the activation/propagation/detection decomposition, the "outputs differ but tests pass" checker-gap predicate and prompt-arm studies of generated verification plans are prior work (functional qualification; Huang et al. 2015; AutoBench lineage; DVBench; the TechRxiv checker-gap preprint; SecTB-RTL). OpenVEF's contribution is the measurement under this specific combination of artifact unit, exposure boundary, fault population and controlled prompt factor, with all artifacts, traces and analyses released. The combination was not found in the sources searched as of [date]; that is not a claim that it has never been done.
If the common-trace checker panel in Section 7 is adopted, add one sentence:
It additionally evaluates every generated checker on a shared set of traces, separating checker sensitivity from the exposure produced by each artifact's own driver.
This statement is defensible because each element it claims (unit, boundary, fault population, factor, release) maps to a cell of the matrix in Section 3 that no reviewed source fills. Every conceptual element is credited to its origin.
7. Methodology concerns and resolution choices
7.1 What PND/(NP+PND) actually measures
Because the mask is checker-independent, exposure is a property of the driver alone. Whether a masked divergence occurs depends only on the driver's stimulus and the mutant. That gives a clean algebraic decomposition, ignoring errors, timeouts and anomalies:
• E_i = (DET_i + PND_i) / N_i: driver exposure rate (checker-free).
• S_i = DET_i / (DET_i + PND_i): own-checker detection given exposure.
• NP_i/N_i ≈ 1 − E_i and PND_i/N_i = E_i · (1 − S_i).
• Therefore miss share = E_i(1 − S_i) / [1 − E_i S_i].
The primary metric is a non-linear blend of a driver quantity and a checker quantity. The same share can come from a strong driver with a weak checker or from a weak driver with a moderately weak checker. It measures the composition of misses for a coupled pair, not checker quality. Report E_i and S_i directly; the share then adds little.
7.2 Can a prompt difference be read causally?
• As a total effect, yes, with conditions. Calls must be independent and order-randomised, and the comparison must not condition on outcomes the prompt affects. A prompt difference in miss share is then a causal effect of the prompt on composition.
• As a mechanism ("structured prompts improve checkers"), no. The prompt acts on the driver and the checker at once; v0.5 cannot separate the two paths.
• v0.5 conditions on post-treatment variables. It analyses only valid artifacts, and only artifacts with MISS_i ≥ 5. If one prompt produces fewer valid artifacts, or artifacts with fewer misses, the compared populations differ and the contrast is no longer a clean total effect. SecTB-RTL's 9 of 1,860 shows how severe validity selection can be. Fix: make validity a co-primary outcome, report the full funnel per scheduled call (intention-to-treat), and label the valid-only comparison as conditional.
7.3 Is checker_gap = PND/(DET+PND) enough?
No. It equals 1 − S_i, which is conditional on the mutants that artifact's own driver exposed. A checker paired with a driver that exposes only easy, gross mutants (an inverted output bit) looks better than the same checker on subtle exposures. The exposure sets differ across artifacts, so S_i is still confounded by the driver.
7.4 Should OpenVEF cross drivers and checkers?
Recommended: yes, in its cheapest form. This is a decision for the owner, and I have not written it into the Charter. The architecture makes crossing almost free. Checkers are pure functions over traces, and every driver's traces on the null netlist and all mutants are already recorded. Crossing needs no new simulation, only more checker evaluations.

7.5 The specification mask: advantages and new risks
Advantages.
• Exposure becomes a checker-free driver property (Section 7.1).
• It is identical across artifacts, so counts are comparable.
• It is frozen before generation, which leaves no room for post hoc boundary choices.
• It aligns "exposure" with what the specification obliges a verifier to check.
New risks.
1.  The experimenter's mask decides the PND count. An over-inclusive mask (for example, every cycle of a status flag) inflates PND for checkers that sensibly check at transaction boundaries. Resolution: pre-register one stricter mask variant (contract-critical outputs and cycles only) as a sensitivity analysis, and have someone other than the mask author review it.
2.  The mask is handed to the generator. v0.5 gives both prompts the observation mask. That is unusual relative to practice, and it tells the checker exactly what to check, which could push PND toward zero and limit external validity. Resolution: decide explicitly. Either keep it and call the condition "mask-informed generation", or give only the specification (the mask is derived from it) and keep the mask for evaluation. This choice matters more for the headline than anything else in the design.
3.  Mapping to checker-dependent schemes. The TechRxiv preprint and Certitude-style taxonomies classify by whether a checker observes an output. Resolution (optional, cheap): wrap the trace object so it logs which signals each checker reads. That yields a checker-dependent classification as a secondary diagnostic, and makes the two schemes comparable rather than merely contrasted.
7.6 Fault model
Yosys/MCY post-synthesis signal mutants are aligned with the claim only if the claim says "structural netlist fault simulation". They are not design-bug mutation; CovR uses the same tool for a similar purpose.
Specific risks:
• Saturation. Inversions on output-cone signals are exposed by almost any driver, so few misses occur and many artifacts fail MISS_i ≥ 5, leaving the primary metric undefined.
• Location skew. Mutants may concentrate in wide datapath bits.
Resolution:
• In F-gate validation, measure the exposure distribution with the random driver only. That uses no LLM artifacts and no outcome peeking.
• Stratify the mutant population descriptively (control/state versus datapath; distance to output).
• Pre-register what happens if the median MISS_i falls below threshold.
• Keep source-level mutants out of the MVP.
7.7 Benchmarks
FIFO and UART TX are adequate engineering choices, but they are not independent of prior work. GateTruth, the TechRxiv preprint, DVBench and the data-integrity paper all use FIFOs, and UART TX appears in GateTruth and the data-integrity paper. There is also a contamination risk: countless FIFO and UART testbenches are in training data, which can produce ceiling effects and erase prompt differences.
Resolution (no scope change):
• Write original cycle-exact specifications with distinctive, non-default semantics. For example: a registered almost_full at a parameterised threshold, a specific simultaneous read/write-at-full rule, UART with configurable parity and a defined break condition.
• Disclose the overlap.
• Treat "two designs" as two strata, not a sample: make no across-design generalisation.
7.8 Is F16 adequate after SecTB-RTL?
In principle, yes. It uses the exact production path, keeps failures in the denominator and includes the null control, which goes beyond SecTB-RTL's schema-only repair. Add five rules:
1.  Pilot both arms and report validity per arm. Pre-register a maximum acceptable validity difference, beyond which H2 becomes conditional-only.
2.  Re-pilot after any contract change. SecTB-RTL's schema-only repair is the cautionary example.
3.  Keep the pilot blind to mutant outcomes. Run pilot artifacts on the null netlist only, or seal mutant results, so the pilot cannot inform delta_checker, mask choices or thresholds.
4.  Pre-register a stop rule, for example: if validity is below the threshold after one repair cycle, the study pauses for redesign rather than expanding the sample.
5.  Include checker-panel compatibility (Option B) in the pilot if B is adopted.
7.9 The prompt manipulation itself
"Identical information, different structure" is hard to guarantee. A structured prompt that says "first list every observable output, then write a check for each" adds attention guidance, which is exactly what SecTB-RTL's equal-attention control exists to neutralise.
Resolution:
• Define allowed differences operationally. Byte-identical content blocks (specification, ports, contract) appear in both prompts. Only ordering, section headers and formatting differ. No added task instructions.
• Token counts must be within a pre-set tolerance.
• An independent reviewer signs a content-equivalence check.
• If step-by-step instructions are wanted, rename the factor "prompt scaffolding" and say it changes attention guidance.
